# 콘텐츠 작성 에이전트 지침

이 지침은 `frontend/content` 아래의 모든 파일에 적용한다.

작업 전에 저장소 루트의 `AGENTS.md`, `REQUIREMENTS.md`, `TECHNICAL_DESIGN.md`, `GLOSSARY.md`와 이 디렉터리의 `CONTENT_FORMAT.md`를 읽는다. 루트 문서가 최종 기준이며, 충돌하면 작업을 멈추고 사용자에게 알린다. 파일 형식은 `CONTENT_FORMAT.md`만 기준으로 삼는다.

## 작성 목표

- 해당 주제를 처음 접하는 개발자가 올바른 개념을 잡도록 설명한다.
- 정확성을 유지하면서 현재 Scene이나 Topic에 필요한 내용만 남긴다.
- 문서에서 아직 소개하지 않은 사전 지식을 독자가 안다고 가정하지 않는다.
- 관련 사실을 모두 나열하기보다 짧고 이해하기 쉬운 설명을 우선한다.

## 작업 순서

1. 현재 Scene과 관련된 부모, 자식, 인접 Scene을 확인한다.
2. 독자가 이해해야 할 내용을 한 문장으로 정한다.
3. 요청 대상이 Scene, 설명, 말단 Topic 또는 퀴즈 중 무엇인지 구분한다. 설명만 요청받았다면 Scene 배치를 수정하지 않는다.
4. 변경될 수 있거나 구현에 따라 다른 사실은 공식 문서나 1차 자료로 확인한다.
5. 작성 후 초보자의 입장에서 중복, 정보량과 흐름을 다시 확인한다.

## 재작성

- 재작성은 기존 문장을 옮기는 일이 아니라 초보자의 학습 순서에 맞춰 설명을 다시 설계하는 일이다.
- 이전 대화의 질문과 답변을 이어 붙이거나 포괄적인 새 제목 아래로 옮기지 않는다.
- 예상 질문이 앞 설명의 부족 때문에 생긴다면 답변을 뒤에 추가하지 말고 관련 설명을 다시 쓴다.
- 남은 내용을 담기 위한 `FAQ`, `보충 설명`, `더 알아보기`, `원리`, `나올 만한 질문` 섹션을 만들지 않는다.
- 사용자가 초안을 먼저 요청하면 문제점과 의도를 정리하고 새 초안을 보여준 뒤 파일을 수정한다.

## 정보 배치

- World Viewport는 위치, 소속, 관계와 흐름을 보여준다.
- Scene 설명은 그림 전체의 의미와 Topic 사이의 관계를 설명한다.
- 말단 Topic 설명은 Topic 하나에 집중한다.
- 자식 Scene의 내부 설명을 부모에서 반복하지 않는다.
- 독립적인 내부 구조나 별도 흐름이 필요한 내용은 자식 Scene으로 만들거나 제안한다.

문서에서는 각 정보의 역할을 분리한다.

- 첫 부분: 무엇이고 왜 보는지
- 기본 개념: 구성 요소와 흐름을 이해하기 위한 선행 개념
- 구성 요소: 현재 Scene에서 각 Topic이 맡는 역할
- 동작 과정: 무엇이 어떤 순서로 일어나는지
- 주제별 내용: `경로 선택`, `서버 인증`처럼 대상이 분명한 추가 설명

같은 내용을 여러 위치에서 반복하거나 계산 원리와 긴 주의사항을 동작 과정에 넣지 않는다. 간단한 Topic은 짧게 끝내며, 세부 내용이 핵심보다 커지면 말단 Topic이나 자식 Scene으로 분리한다.

## 개발자가 개입하는 지점

- 개발자가 바꿀 수 있는 설정, 확장 지점이나 작성할 코드를 구체적으로 설명한다.
- 이해에 도움이 될 때만 짧은 코드 예제를 넣는다.
- 직접 객체를 만들지 않아도 설정으로 동작을 바꾼다면 그 지점을 설명한다.
- 직접 개입할 지점이 없다면 없다고 밝히고, 알아야 하는 이유를 디버깅이나 문제 추적 관점에서 설명한다.
- 개발자 개입이 문서 목적과 무관한 Topic에는 이 내용을 억지로 추가하지 않는다.

## 문장과 용어

- 일반 단어는 `데이터`, `브라우저`, `서버`, `네트워크`, `키`처럼 한국어로 쓴다.
- 정확한 Class, Method, Protocol Message와 고유 기술명은 원문을 유지한다. 예: `SecurityFilterChain`, `chain.doFilter()`, `ClientHello`, `Key Share`.
- `GLOSSARY.md`의 권장 용어를 따른다.
- 전문 용어는 처음 필요한 위치에서 짧게 설명한다.
- 한 문단에는 중심 내용 하나만 두고 긴 문장은 나눈다.
- 영어, 제목, 강조, Code Block과 Text Diagram을 과하게 사용하지 않는다.

## 정확성

- 검증된 사실, 일반적인 구조 예시와 프로젝트의 가정을 구분한다.
- 공식 문서와 1차 자료를 우선한다.
- 사실을 틀리게 단순화하지 말고 설명 범위를 줄인다.
- 구현 차이는 `일반적으로`, `구현에 따라`, `SQL 표준 기준으로`처럼 범위를 밝힌다.
- 이름이 비슷해도 기술적으로 다른 개념은 구분한다.
- 공개되지 않은 Google 내부 구현을 아는 것처럼 작성하지 않는다.

## 퀴즈와 공통 Concept

- 퀴즈는 본문으로 답할 수 있는 핵심 관계나 흔한 오해를 묻는다.
- 질문 하나에는 내용 하나만 담고 정답은 결론부터 한두 문장으로 쓴다.
- 함정 문제, 중복 질문과 퀴즈에서 처음 등장하는 핵심 정보는 만들지 않는다.
- 위치와 무관하게 재사용할 핵심 원리만 공통 Concept로 분리한다.
- 현재 흐름의 사용 맥락과 구현별 설명은 해당 Scene이나 Topic에 남긴다.

## 완료 보고

변경한 파일을 모두 알리고, 프로젝트 규칙에 따라 테스트를 실행하지 않았다고 명시한다. 충족하지 못한 항목이 있다면 함께 보고한다.
