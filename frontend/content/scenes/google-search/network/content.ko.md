# 네트워크

## 개요

브라우저는 검색 서비스의 호스트 이름을 네트워크 주소로 확인하고, 그 주소를 향해 요청을 보낼 준비를 합니다. DNS 결과나 기존 연결이 캐시에 남아 있다면 일부 단계는 생략되거나 재사용될 수 있습니다.

## 필요한 이유

애플리케이션이 사용하는 호스트 이름만으로는 IP 네트워크의 목적지를 바로 지정할 수 없습니다. 이름을 주소로 해석하고, 선택한 전송 방식과 보안 프로토콜에 맞는 통신 상태를 준비해야 요청을 원격 서비스까지 전달할 수 있습니다.

## 동작 과정

1. 브라우저가 요청 대상 호스트 이름을 확인합니다.
2. 필요한 경우 DNS 이름 확인을 수행합니다.
3. 확보한 주소와 요청 조건을 사용해 전송 연결을 준비합니다.
4. 보안 연결이 필요한 경우 상대 endpoint를 확인하고 암호화된 통신 상태를 만듭니다.
5. 준비된 경로를 통해 요청을 서비스 endpoint로 보냅니다.

## 내부 구조

이 장면은 이름 확인과 요청 전송 사이의 관계를 보여주는 일반 웹 아키텍처 예시입니다. DNS Topic은 현재 게시되어 있으며, 전송 연결과 보안 요청의 상세 장면은 준비 중입니다. Google 내부 네트워크의 비공개 구성은 표현하지 않습니다.

## 실패 상황

- DNS 응답을 얻지 못하거나 잘못된 주소가 캐시될 수 있습니다.
- 목적지까지의 경로에서 packet 손실이나 시간 초과가 발생할 수 있습니다.
- 연결 수립, 인증서 확인 또는 보안 협상에 실패할 수 있습니다.
- 기존 연결을 재사용하려 했지만 상대가 이미 연결을 닫았을 수 있습니다.

## 실무 맥락

DNS 조회 시간, 연결 시간, 보안 협상 시간과 첫 응답 시간은 서로 다른 지표입니다. 단순히 “네트워크가 느리다”고 묶지 않고 각 구간을 나누어 측정해야 병목을 찾을 수 있습니다.

## 관련 개념

DNS 이름 확인을 선택하면 resolver, cache와 이름 서버 질의의 관계를 볼 수 있습니다. 이후 전송 연결과 보안 요청은 별도 내부 흐름이 게시되면 같은 공간 안에서 확대할 수 있습니다.
