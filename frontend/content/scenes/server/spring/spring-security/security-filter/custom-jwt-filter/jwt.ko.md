# 한눈에 보기

JWT는 사용자 식별 정보와 권한 등의 데이터를 `JSON 구조`로 표현하여 전달하는 토큰 형식입니다.
`Header, Payload, Signature`로 구성되며, Signature를 통해 데이터의 `무결성과 서명의 유효성`을 검증합니다.
대표적인 서명 알고리즘으로는 대칭키 기반의 `HMAC`과 비대칭키 기반의 `RSA`가 있으며, 각각 HS256과 RS256 등에 사용됩니다.
서버는 별도의 세션 조회 없이 JWT를 검증할 수 있으므로 Stateless 인증 구조를 구현하는 데 활용할 수 있습니다.

---

# JWT란?

JWT는 `사용자 식별 정보`나 권한 등의 `속성 정보를 JSON 구조`로 표현하여 전달하는 토큰 형식입니다.
인증 시스템에서는 사용자가 로그인한 이후 발급받은 JWT를 서버에 전달하고, 서버는 토큰에 포함된 정보를 검증하여 사용자를 식별할 수 있습니다.
여기서 중요한 점은 JWT가 단순히 사용자 정보를 담는 문자열이 아니라, `해당 정보의 무결성과 출처를 검증`할 수 있도록 설계된 토큰 형식이라는 것입니다.

---

# JWT의 구조

JWT는 JSON 데이터를 단순히 문자열로 변환한 것이 아닙니다.
일반적으로 사용하는 서명 기반 JWT는 Header, Payload, Signature의 세 부분으로 구성됩니다.

```text
Header.Payload.Signature
```

- `Header`: 토큰의 유형과 서명 알고리즘 등의 정보를 포함합니다.
- `Payload`: 사용자 식별 정보, 권한, 만료 시간 등의 데이터를 포함합니다.
- `Signature`: Header와 Payload의 무결성 및 서명의 유효성을 검증하는 데 사용됩니다.

Header와 Payload는 JSON 데이터를 `Base64URL로 인코딩`하며, Signature 역시 Base64URL로 인코딩하여 하나의 문자열로 결합합니다.
Base64URL은 바이너리 데이터를 URL에서 안전하게 사용할 수 있는 문자 집합으로 표현하는 인코딩 방식입니다.
이러한 인코딩을 통해 각 부분을 안전하게 문자열로 전달하고 구분할 수 있습니다.
중요한 점은 Base64URL이 암호화가 아니라는 것입니다. `누구나 디코딩`할 수 있으므로 Payload에 비밀번호와 같은 `민감한 정보를 직접 포함해서는 안 됩니다.`

# Signature는 왜 필요할까?

JWT의 Payload에는 사용자 식별 정보나 권한 등이 포함될 수 있습니다.
그런데 Payload는 Base64URL로 인코딩되어 있을 뿐이므로 누구나 내용을 확인하고 변경할 수 있습니다.
그렇다면 서버는 클라이언트가 전달한 사용자 정보가 실제로 신뢰할 수 있는 발급자로부터 생성되었으며, 중간에 변경되지 않았다는 사실을 어떻게 확인할 수 있을까요?
이를 위해 Signature를 사용합니다.
Signature는 `토큰의 무결성과 서명의 유효성을 검증`하기 위한 값입니다.
서명 검증에 성공하면 신뢰하는 키를 사용하여 생성된 서명이며, 서명 대상 데이터가 변경되지 않았다는 사실을 확인할 수 있습니다.

## 무결성 검증과 해시 함수

무결성이란 데이터가 의도하지 않게 변경되거나 위변조되지 않았음을 의미합니다.
무결성 검증을 이해하기 위해서는 먼저 `해시 함수`를 알아야 합니다.
해시 함수는 입력 데이터를 고정된 길이의 해시값으로 변환하는 함수입니다.
대표적으로 SHA-256이 있으며, 입력 데이터가 조금만 변경되어도 출력되는 해시값이 크게 달라지는 `눈사태 효과`를 가지고 있습니다.

```text
SHA256("USER")  → 해시값 A
SHA256("ADMIN") → 해시값 B
```

두 데이터의 `해시값이 다르다면 입력 데이터가 같지 않다`는 사실을 확인할 수 있습니다.
SHA-256은 256비트의 해시값을 생성하며, 충돌 저항성과 역상 저항성 등의 보안 특성을 제공하기 때문에 무결성 검증과 디지털 서명에 널리 사용됩니다.
하지만 여기에는 한 가지 문제가 있습니다.

## 해시값 자체를 신뢰할 수 있을까?

SHA-256은 누구나 사용할 수 있는 공개된 해시 알고리즘입니다.
따라서 공격자가 Payload를 변경한 다음 `새로운 해시값을 계산하는 것도 가능`합니다.

```text
정상 데이터
USER → SHA256 → 해시값 A

공격자가 변경한 데이터
ADMIN → SHA256 → 해시값 B
```

서버가 전달된 데이터와 해시값만으로 무결성을 검증한다면, 공격자가 두 값을 모두 변경했을 때 이를 `신뢰할 수 있는 발급자가 생성한 것인지 구분할 수 없습니다`.
즉, 해시 함수만으로는 데이터의 변경 여부를 확인할 수는 있어도, 해당 해시값을 누가 생성했는지까지 증명할 수 없습니다.
그렇다면 이를 어떻게 해결할 수 있을까요? 바로 서버만 알고 있는 `비밀키를 사용`하는 것입니다.

## HMAC

HMAC은 `해시 함수와 비밀키를 함께 사용`하여 메시지 인증 코드를 생성하는 알고리즘입니다.
SHA-256이 입력 데이터만으로 해시값을 생성한다면, HMAC은 입력 데이터와 비밀키를 함께 사용합니다.
따라서 공격자가 데이터를 변경하고 해시 함수를 알고 있더라도, `비밀키를 모른다면 올바른 HMAC 값을 생성할 수 없습니다.`

```text
[HMAC 생성]
HMAC(원본 데이터, 비밀키) = 인증 코드 A

[HMAC 검증]
HMAC(전달받은 데이터, 비밀키) = 인증 코드 B

A == B → 검증 성공
```

서버는 전달받은 데이터와 자신이 보유한 비밀키를 이용하여 HMAC 값을 다시 계산하고, 전달된 인증 코드와 비교합니다.
두 값이 일치한다면 해당 비밀키를 알고 있는 주체가 생성한 인증 코드이며, 데이터가 변경되지 않았다는 사실을 확인할 수 있습니다.
즉, HMAC은 단순한 해시 함수와 달리 비밀키를 이용하여 `데이터의 무결성과 출처에 대한 신뢰를 확보`하는 방식입니다.

# JWT의 서명 알고리즘

JWT의 Signature는 서명 알고리즘과 키를 이용해 생성됩니다.
대표적인 방식으로 HS256과 RS256이 있습니다.

## HS256과 HMAC

HS256은 `HMAC-SHA256을 사용하는 대칭키 기반` 서명 알고리즘입니다.
HMAC은 해시 함수와 비밀키를 함께 사용하여 메시지 인증 코드를 생성하는 방식입니다.
SHA-256만으로 해시값을 생성하는 것과 달리, 비밀키를 알지 못하면 정상적인 HMAC 값을 생성하기 어렵습니다.
JWT의 HS256은 다음과 같은 방식으로 Signature를 생성합니다.

```text
Signature = HMAC-SHA256(Base64URL(Header) + "." + Base64URL(Payload), SecretKey)
```

서버는 동일한 비밀키를 이용하여 Signature를 다시 계산하고, 토큰에 포함된 Signature와 비교합니다.

```text
[HMAC 생성]
HS256(원본 데이터, 비밀키) = 인증 코드 A

[HMAC 검증]
HS256(전달받은 데이터, 비밀키) = 인증 코드 B

A == B → 검증 성공
```

검증에 성공했다면 비밀키를 알고 있는 주체가 생성한 유효한 서명이며, 서명 대상 데이터가 변경되지 않았다는 사실을 확인할 수 있습니다.
다만 HS256에는 한 가지 특징이 있습니다.
`토큰을 생성하는 서버와 검증하는 서버 모두 동일한 비밀키를 알고 있어야 한다는 것입니다.` 즉, 검증 권한을 가진 서버는 동시에 새로운 토큰을 생성할 수 있는 능력도 가지게 됩니다.
따라서 여러 서버가 동일한 비밀키를 공유한다면, 어느 한 서버에서 `비밀키가 유출`되었을 때 다른 서버에서도 유효한 것으로 인정되는 `토큰을 위조할 위험`이 있습니다.

## RS256과 RSA

HS256이 하나의 비밀키로 서명 생성과 검증을 모두 수행한다면, RS256은 서로 다른 키를 사용하는 `비대칭키 기반 서명 알고리즘`입니다.
RS256은 RSA와 SHA-256을 결합한 디지털 서명 방식으로, 개인키와 공개키를 사용합니다.

- `개인키`: JWT의 Signature를 생성합니다.
- `공개키`: JWT의 Signature를 검증합니다.

개인키와 공개키는 수학적으로 연결되어 있기 때문에 서로 다른 키를 사용하더라도 서명을 검증할 수 있습니다.

```text
[JWT 발급 서버]
RS256(Header, Payload, 개인키)
= Signature A

[JWT 검증 서버]
RS256(Header, Payload, Signature A, 공개키)
= 성공 / 실패
```

이 방식의 가장 큰 장점은 `서명 생성 권한과 검증 권한을 분리`할 수 있다는 것입니다.
예를 들어 인증 서버만 개인키를 가지고, 여러 리소스 서버에는 공개키만 제공할 수 있습니다.
그러면 리소스 서버는 JWT를 독립적으로 검증할 수 있지만, 공개키만으로는 새로운 유효한 JWT를 생성할 수 없습니다.
따라서 검증 서버의 공개키가 노출되더라도 개인키가 유출된 것과 같은 위험이 발생하지 않습니다. 공개키는 원래 외부에 공개할 수 있도록 설계된 키이기 때문입니다.
이러한 특성으로 인해 RS256은 토큰 발급 서버와 검증 서버가 분리된 환경에서 활용하기 좋습니다.

# 서명 검증에 성공하면 인증도 성공할까?

Signature 검증에 성공했다고 해서 해당 JWT를 무조건 신뢰할 수 있는 것은 아닙니다.
Signature는 서명 대상 데이터가 변경되지 않았으며, 신뢰하는 키에 대응하는 유효한 서명이라는 사실을 검증할 뿐입니다.
실제 인증 과정에서는 추가적으로 다음과 같은 정보를 확인해야 합니다.

- `exp`: 토큰의 만료 시간이 지나지 않았는가?
- `iss`: 신뢰할 수 있는 발급자가 발급한 토큰인가?
- `aud`: 현재 서버를 대상으로 발급한 토큰인가?
- `sub`: 토큰이 나타내는 사용자는 누구인가?

또한 서버는 허용할 서명 알고리즘과 검증 키를 신뢰할 수 있는 설정에 따라 선택해야 하며, Header에 작성된 알고리즘을 무조건 신뢰해서는 안 됩니다.
결국 JWT 인증은 단순히 Signature를 비교하는 과정이 아니라, 서명 검증과 토큰의 유효성 검사를 함께 수행하는 과정입니다.
