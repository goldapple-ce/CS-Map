# 한눈에 보기

Immutability는 객체 생성 이후 `상태를 변경할 수 없도록` 하여 공유 가변 상태로 인한 동시성 문제를 예방하는 특성입니다.
`final`은 불변성을 구현하는 수단 중 하나이며, 핵심은 객체의 상태가 변경될 수 있는 경로를 차단하는 것입니다.
불변 객체는 여러 스레드가 안전하게 공유할 수 있지만, `객체의 안전한 전달과 공유 참조의 갱신은 별도로 고려`해야 합니다.

---

# Immutability란?

Immutability는 객체가 생성된 이후 `상태를 변경할 수 없는 특성`을 의미합니다.
불변 객체는 여러 스레드가 동일한 객체를 공유하더라도 상태가 변경되지 않으므로, 공유 상태의 변경으로 인한 Race Condition을 방지할 수 있습니다.

Lock-Based나 Lock-Free가 공유 가변 상태에 대한 동시 접근을 제어하는 방식이라면, Immutability는 `객체의 가변 상태 자체를 제거`하여 동시성 문제를 예방하는 방식입니다.

---

# Immutability가 필요한 이유

여러 스레드가 동일한 가변 객체를 공유하고 변경하면, 작업이 서로 간섭하여 Race Condition이 발생할 수 있습니다.
이를 방지하기 위해 Lock을 사용하거나 원자적 연산을 활용할 수 있지만, 모든 공유 객체에 이러한 동기화가 필요한 것은 아닙니다.

객체가 생성된 이후 상태를 변경할 필요가 없다면, 불변 객체로 설계하여 여러 스레드가 안전하게 공유하도록 할 수 있습니다.

예를 들어 애플리케이션의 설정 정보처럼 여러 스레드가 동일한 데이터를 읽어야 하지만 변경할 필요는 없는 경우가 있습니다.
이러한 객체를 불변으로 설계하면 스레드 간 변경 충돌이 발생하지 않으므로 별도의 Lock 없이 데이터를 읽을 수 있습니다.

즉, Immutability는 공유 자체를 제거하는 것이 아니라 `공유하더라도 변경할 수 없는 상태를 만드는 것`입니다.

---

# 불변 객체를 구현하는 방법

Java에서 불변 객체를 구현하는 핵심은 생성 이후 객체의 상태가 변경될 수 있는 경로를 차단하는 것입니다.

일반적으로 다음 원칙을 적용합니다.

1. `상태 변경 제한`: 객체 생성 이후 필드나 내부 객체의 상태를 변경하는 메서드를 제공하지 않습니다.
2. `접근 제한`: 필드를 private으로 선언하여 외부에서 직접 변경하지 못하도록 합니다.
3. `가변 객체 보호`: 내부에 가변 객체가 있다면 방어적 복사 등을 통해 외부의 변경이 영향을 미치지 않도록 합니다.
4. `상속 제한`: 하위 클래스가 불변성을 깨뜨리지 못하도록 상속을 제한하거나 적절하게 설계합니다.

다음은 불변 객체를 구현한 예시입니다.

```java
public class Main {
    static final class User {
        private String name;
        private List<String> roles;

        User(String name, List<String> roles) {
            this.name = name;
            this.roles = List.copyOf(roles);
        }

        String getName() {
            return name;
        }

        List<String> getRoles() {
            return roles;
        }
    }

    public static void main(String[] args) {
        List<String> roles = new ArrayList<>(List.of("USER"));
        User user = new User("Kim", roles);

        roles.add("ADMIN");

        System.out.println(user.getRoles()); // [USER]
    }
}
```

위 코드에서는 필드에 final을 선언하지 않았지만, 생성 이후 상태를 변경하는 메서드가 없으므로 일반적인 접근으로는 객체의 상태를 변경할 수 없습니다.
또한 `List.copyOf()`를 이용해 전달받은 리스트를 보호하므로, 외부 리스트가 변경되더라도 User의 내부 상태에는 영향을 미치지 않습니다. 이 예시에서는 리스트의 요소인 String 역시 불변 객체입니다.
클래스를 final로 선언한 이유는 하위 클래스가 가변 상태를 추가하여 불변성을 깨뜨리는 것을 방지하기 위해서입니다.
따라서 불변 객체를 구현할 때 중요한 것은 `final 선언 자체가 아니라 객체의 상태가 변경되지 않도록 보장하는 것`입니다.

# Immutability와 final의 관계

Java에서 final은 불변 객체를 구현하는 데 유용하지만, 불변성을 보장하기 위한 필수 조건은 아닙니다.

- `private`: 외부에서 필드에 직접 접근하지 못하도록 제한합니다.
- `final field`: 필드가 초기화된 이후 다른 값을 재할당하지 못하도록 제한합니다.
- `final class`: 상속을 제한하여 하위 클래스에서 불변성을 깨뜨리지 못하도록 합니다.

하지만 final 필드라고 해서 참조하는 객체의 내부 상태까지 불변이 되는 것은 아닙니다.

```java
final List<String> names = new ArrayList<>();

names.add("Kim"); // 변경 가능
```

final은 names가 참조하는 객체를 다른 객체로 교체하지 못하도록 제한할 뿐, 리스트의 내부 상태 변경까지 막지는 않습니다.

반대로 final이 없더라도 상태를 변경할 수 있는 경로가 없다면 불변 객체를 구현할 수 있습니다.
다만 private과 setter의 부재만으로 충분한 것은 아니며, 클래스 내부의 다른 메서드나 참조 객체를 통한 변경 가능성까지 고려해야 합니다.

## Reflection을 통한 변경

final은 일반적인 Java 코드에서 필드의 재할당을 제한하지만, `Reflection과 같은 특수한 접근까지 모든 경우에 차단하는 것은 아닙니다.`
일부 final 인스턴스 필드는 Reflection을 통해 변경할 수 있으며, 접근 권한이나 필드 종류, Java 버전에 따라 제한이 달라집니다.
특히 JDK 26부터는 Reflection을 이용한 final 필드 변경에 기본적으로 경고가 발생하며, 향후에는 명시적인 허용 없이 변경하는 것을 차단하도록 제한이 강화될 예정입니다.
따라서 불변성은 Reflection과 같은 강제적인 내부 변경까지 절대적으로 차단한다는 의미보다는, `객체가 정상적으로 사용되는 과정에서 상태가 변경되지 않도록 설계된 특성`으로 이해하는 것이 적절합니다.

# Immutability와 Thread Safety

Immutability는 Thread Safety를 달성하기 위한 대표적인 방법 중 하나입니다.
여러 스레드가 동일한 가변 객체를 수정한다면 적절한 동기화가 필요하지만, 불변 객체는 생성 이후 상태가 변경되지 않으므로 읽기 작업끼리 서로 간섭하지 않습니다.
따라서 `올바르게 생성되고 다른 스레드에 안전하게 전달된 불변 객체`는 별도의 Lock 없이 여러 스레드가 함께 읽을 수 있습니다.
다만 불변 객체를 사용한다고 해서 모든 동시성 문제가 해결되는 것은 아닙니다.

## 공유 참조의 변경

불변 객체는 내부 상태를 변경할 수 없으므로, 값을 변경하려면 새로운 객체를 생성해야 합니다.
그런데 여러 스레드가 공유하는 참조를 새로운 불변 객체로 교체한다면, `참조를 읽고 변경하는 과정에서 Race Condition`이 발생할 수 있습니다.

따라서 불변 객체 자체의 스레드 안전성과 공유 참조를 변경하는 작업의 스레드 안전성은 구분해야 합니다.
이러한 경우 AtomicReference나 Lock-Based 방식 등의 동기화가 필요할 수 있습니다.

## JMM과 final

final 필드는 단순히 재할당을 제한하는 것 외에도 JMM에서 특별한 초기화 안전성을 제공합니다.
객체가 생성 과정에서 외부로 노출되지 않고 final 필드가 올바르게 초기화되었다면, 다른 스레드가 해당 객체를 참조할 때 final 필드의 초기화된 값을 관찰하도록 보장합니다.
반면 final이 없는 불변 객체는 상태가 변경되지 않더라도, 다른 스레드에 초기화된 상태가 올바르게 전달되도록 안전한 게시가 필요합니다.
따라서 final은 불변성의 필수 조건은 아니지만, `불변 객체를 스레드 간에 안전하게 공유하는 데 중요한 역할`을 합니다.

# Immutability와 ThreadLocal의 차이

ThreadLocal과 Immutability는 모두 공유 가변 상태로 인한 동시성 문제를 줄이지만, 접근 방식이 다릅니다.

- ThreadLocal: 스레드마다 독립적인 상태를 유지하여 공유할 필요가 없는 데이터를 격리합니다.
- Immutability: 객체의 상태 변경을 제한하여 여러 스레드가 동일한 객체를 안전하게 공유하도록 합니다.

즉, ThreadLocal은 `불필요한 공유를 제거`하는 방식이고, Immutability는 `공유하더라도 변경되지 않도록 만드는` 방식입니다.
따라서 여러 스레드가 동일한 데이터를 읽어야 한다면 불변 객체가 적합하고, 스레드마다 독립적인 데이터를 관리해야 한다면 ThreadLocal을 고려할 수 있습니다.
