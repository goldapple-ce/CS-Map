# 한눈에 보기

OOP는 프로그램을 객체들의 협력으로 구성하는 프로그래밍 패러다임입니다.  
이 글에서는 다음 내용을 다룹니다.

- OOP가 무엇인지
- 객체지향 설계 원칙인 SOLID
- OOP의 4대 특징인 캡슐화, 상속, 추상화, 다형성

---

# OOP(객체지향 프로그래밍)이란?

Java나 C++ 같은 객체지향 언어를 배우면 가장 먼저 접하게 되는 개념 중 하나입니다.  
하지만 객체지향 프로그래밍은 하나의 문장으로 딱 정의하기 어렵습니다. 사람마다 중요하게 보는 부분이 조금씩 다르기 때문입니다.

- Alan Kay : 객체가 자신의 상태와 동작을 내부에 감추고, 다른 객체와 메시지를 주고받으며 협력하고, 가능한 결정을 늦게 바인딩하는 프로그래밍 방식.
- Grady Booch : 프로그램을 서로 협력하는 객체들의 집합으로 구성하는 프로그래밍 방식.
- Robert C. Martin(Uncle Bob) : 동적 다형성을 이용해 호출하는 코드가 구체적인 구현 코드에 직접 의존하지 않도록 만드는 프로그래밍 방식.
- 일반적인 정의 : 프로그램을 역할과 책임을 가진 객체들로 구성하고, 객체들이 서로 상호작용하며 기능을 수행하도록 설계하는 프로그래밍 패러다임.

표현은 다르지만 공통적으로는 `프로그램을 역할과 책임을 가진 객체들로 나누고, 객체들의 협력을 통해 기능을 구성한다`는 것입니다.

그리고 그 목적은 결국 다음과 같습니다.

> 어떻게 하면 변경의 영향을 줄이고 유지보수하기 쉬운 프로그램을 만들 수 있을까?

---

# OOP의 5대 원칙 : SOLID

SOLID는 객체지향 설계에서 자주 사용하는 다섯 가지 원칙의 앞글자를 모은 이름입니다.

목적은 변경의 영향을 줄이고, 결합도를 낮추며, 확장과 유지보수를 쉽게 만드는 것입니다.

- `SRP(Single Responsibility Principle)` : 하나의 클래스는 하나의 변경 이유만 가져야 합니다.
- `OCP(Open-Closed Principle)` : 확장에는 열려 있고 수정에는 닫혀 있어야 합니다.
- `LSP(Liskov Substitution Principle)` : 하위 타입은 상위 타입을 문제없이 대체할 수 있어야 합니다.
- `ISP(Interface Segregation Principle)` : 사용하지 않는 기능까지 의존하도록 강요해서는 안 됩니다.
- `DIP(Dependency Injection Principle)` : 구체적인 구현보다 추상화에 의존해야 합니다.

SOLID를 관통하는 핵심은 변경의 영향을 가능한 좁은 범위에 가두는 것이라고 볼 수 있습니다.

- `SRP`, `ISP`는 책임과 의존성을 분리합니다.
- `LSP`는 상속과 다형성 구조의 신뢰를 보장합니다.
- `OCP`, `DIP`는 추상화를 통해 구현 변경이 다른 코드로 퍼지는 것을 줄입니다.

# OOP의 4대 특징 : 캡상추다

객체지향을 설명할 때 흔히 다음 네 가지를 OOP의 4대 특징이라고 부릅니다.

- `캡슐화(Encapsulation)` : 데이터와 기능을 하나로 묶고 내부 구현을 외부로부터 숨기는 것입니다.
- `상속(Inheritance)` : 기존 타입의 특성과 동작을 물려받아 새로운 타입을 정의하는 것입니다.
- `추상화(Abstraction)` : 필요한 특징만 드러내고 복잡한 내부 구현은 감추는 것입니다.
- `다형성(Polymorphism)` : 같은 타입으로 여러 객체를 다루면서, 객체에 따라 서로 다른 동작을 수행할 수 있는 성질입니다.

이 네 가지는 객체지향의 공식적인 정의라기보다 객체지향에서 반복적으로 사용되는 대표적인 특징을 정리한 것에 가깝습니다.

## 뭐가 제일 중요할까?

네 가지 모두 중요하지만, 하나를 고르라면 `다형성`을 가장 중요하게 보는 경우가 많습니다.

다형성의 핵심은 단순히 같은 메서드가 다르게 실행된다는 것이 아닌, 사용하는 쪽이 구체적인 구현을 몰라도 된다는 것이 더 중요합니다.

```java
interface Payment {
    void pay();
}

class CardPayment implements Payment { ... }
class KakaoPayment implements Payment { ... }
```

사용하는 쪽은 `CardPayment`나 `KakaoPayment`가 아니라 `Payment`에만 의존하면 됩니다.

```text
OrderService → Payment
                 ↑
      CardPayment / KakaoPayment
```

그래서 결제 방식이 추가되거나 변경되어도 사용하는 코드에 미치는 영향을 줄일 수 있습니다.

이 지점에서 SOLID와도 연결됩니다.

- `OCP` : 기존 코드를 수정하지 않고 새로운 구현을 추가할 수 있습니다.
- `LSP` : 서로 다른 구현이 같은 타입으로 안전하게 대체될 수 있어야 합니다.
- `DIP` : 사용하는 쪽이 구체 클래스가 아니라 추상화에 의존합니다.

결국 다형성이 중요한 이유는 구체적인 구현의 변경으로부터 사용하는 코드를 보호할 수 있기 때문입니다.
