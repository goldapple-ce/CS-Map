# 한눈에 보기

HTTPS는 HTTP 데이터를 TLS로 암호화해 전송하는 프로토콜입니다.

브라우저와 서버는 암호화된 데이터로 통신합니다. 중간에서 데이터를 훔쳐보더라도 암호화되어 있어 원래 내용을 바로 읽기 어렵습니다.

암호화하려면 양쪽이 같은 암호화 기준을 준비해야 합니다. 데이터를 보내기 전에 서버를 확인하고 키를 만드는 과정이 `TLS Handshake`이며, 뷰포트 그림은 이 과정을 보여줍니다.

---

# 기본 개념

- `암호화 / 복호화`: 데이터를 알아보기 어렵게 바꾸는 것이 암호화이고, 원래 내용으로 되돌리는 것이 복호화입니다.
- `대칭키 / 비대칭키`: 대칭키는 암호화와 복호화에 같은 비밀키를 사용합니다. 비대칭키는 서로 다른 공개키와 비공개키를 한 쌍으로 사용합니다.
- `공개키 / 비공개키`: 공개키는 다른 사람에게 공개해도 되지만, 비공개키는 소유자만 보관해야 합니다.
- `Certificate`: 서버가 진짜임을 증명하는 인증서입니다. 서버의 도메인과 공개키가 들어 있습니다.
- `세션키`: 브라우저와 서버가 실제 데이터를 암호화할 때 사용하는 대칭키입니다.
- `Key Share`: 세션키를 만들기 위해 브라우저와 서버가 주고받는 재료입니다.

---

# 구성 요소

- `CA`: `Certificate Authority`의 약자로 인증서를 발급하고 서명하는 인증 기관입니다.
- `브라우저`: TLS Handshake를 시작하고 서버가 보낸 인증서를 검증합니다.
- `서버`: CA에서 발급받은 인증서를 브라우저에 보내고 암호화 통신을 준비합니다.

---

# 동작 과정

1. `TCP Handshake`: 브라우저와 서버가 먼저 연결합니다. 자세한 과정은 TCP 토픽에서 다룹니다.
2. `ClientHello`: 브라우저가 Client Key Share `A`를 서버에 보냅니다.
3. `ServerHello`: 서버가 Server Key Share `B`를 브라우저에 보냅니다.
4. `세션키 준비`: 브라우저와 서버는 서로 교환한 key Share를 기반으로 `세션키를 각각 만듭니다`. 이에 대한 자세한 내용은 아래에서 설명하겠습니다.
5. `Certificate 전달`: 서버가 인증서와 전자서명을 브라우저에 보냅니다.
6. `서버 확인`: 브라우저가 내장된 Root CA 정보를 이용해 인증서의 서명, 도메인과 유효기간을 확인합니다. 이때 CA 서버에 매번 요청하지는 않습니다.
7. `암호화 통신`: 인증까지 완료되면 브라우저와 서버가 세션키로 HTTP 요청과 응답을 암호화합니다.

---

# 세션 키를 만드는 방법

Browser와 Server는 서로 교환한 `Key Share`를 기반으로, 각자 가지고 있는 비공개키를 이용해 같은 공유 비밀을 계산합니다.

설명을 단순화하면 다음과 같습니다.

```text
공개된 공통값: G

Browser의 비공개키: a
Browser의 Key Share(공개키): A = a × G

Server의 비공개키: b
Server의 Key Share(공개키): B = b × G
```

Browser는 Server가 보낸 `B`에 자신의 비공개키 `a`를 사용합니다.

```text
a × B = a × (b × G) = a × b × G
```

Server는 Browser가 보낸 `A`에 자신의 비공개키 `b`를 사용합니다.

```text
b × A = b × (a × G) = a × b × G
```

계산 순서만 다르고 결과는 같습니다. 따라서 완성된 비공개키을 전송하지 않아도 Browser와 Server가 같은 대칭키를 얻습니다.

---

# Key Share가 노출되어도 되는 이유

Network를 지켜보는 공격자는 다음 값을 모두 볼 수 있습니다.

```text
G, A = a × G, B = b × G
```

하지만 Browser의 비공개키 `a`와 Server의 비공개키 `b`는 전송되지 않습니다.  
공격자가 `G`와 `A`를 안다고 해도 `a`를 역으로 계산하는 것은 현실적인 시간 안에 매우 어렵습니다. `B`에서 `b`를 찾는 것도 마찬가지입니다.

따라서 공격자는 Key Share를 모두 탈취해도 세션키를 계산할 수 없습니다.

---

# Key Share를 바꿔치기하면 어떻게 될까?

엿보기만 하는 공격자는 비공개키을 알아낼 수 없지만, Key Share를 자신의 값으로 바꿔치기하는 공격은 별도로 막아야 합니다.

Server는 인증서 비공개키로 현재 Handshake 내용에 서명한 `CertificateVerify`를 보냅니다. Browser는 인증서의 공개키로 이 서명을 검증합니다.

공격자가 Key Share를 바꾸면 Handshake 내용도 달라지므로 올바른 서명을 만들 수 없습니다. 마지막 `Finished` 검증에서도 변조가 발견되어 연결이 중단됩니다.

---

# 왜 대칭키를 사용할까?

공개키와 비공개키를 사용하는 비대칭키 방식으로도 데이터를 암호화할 수 있습니다.

하지만 계산 비용이 크고 한 번에 처리할 수 있는 데이터에도 제약이 있어, 많은 HTTP 데이터를 계속 주고받는 용도로는 비효율적입니다.

대칭키 방식은 같은 수준의 보안을 목표로 할 때 훨씬 빠르게 많은 데이터를 처리할 수 있습니다.
